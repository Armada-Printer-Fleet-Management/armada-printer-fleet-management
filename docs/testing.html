Testing the server

How the server's tests are organised, and why. This page is the quick picture. The rules everyone follows when writing a test, people and agents alike, are in apps/server/tests/AGENTS.md.

In short

  • Three sizes, one dividing line. A test's size depends on how many real programs it runs, not on how many functions it touches.
  • Most tests are unit tests. They are fast and dependable, so they can cover everything the server decides.
  • Larger tests catch what smaller ones cannot. A larger test is only worth its extra time if it could fail while every smaller test passes.

Why it works this way

  • Mock as little as possible. An imitation can quietly stop matching the real thing, and then tests keep passing while the product is broken.
  • Use real dependencies where it counts. Only a real database or file store can show how they really behave, and whether the server is wired to them correctly.
  • A failing test always means something. Unit and integration tests are never quietly skipped or retried, so a pass really is a pass, and a single failure gets looked at.
