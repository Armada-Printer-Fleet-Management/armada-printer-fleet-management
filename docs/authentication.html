Authentication and authorization

How a person proves who they are, how the server decides what they may do, and the accounts developers sign in with.

From sign-in to an allowed request

Nobody signs in to the server itself. Keycloak, the identity provider, checks the password and hands back an access token naming the person's roles. Every request then carries that token, and the server only has to check it, never a password. Keycloak's armada realm is the source of truth for who has which role.

Roles

Four realm roles, from least to most access: guest, student, staff and admin. Students submit and follow their own prints. Staff and admins run the fleet: review jobs, dispatch, and see every printer. Each endpoint lists the roles it allows, in one table on the server, so what a role can reach is read in one place rather than scattered through handlers.

Until enforcement is switched on, the server lets every request through and logs the ones it would refuse as access would be denied. That keeps development moving while sign-in is being built, and shows exactly which calls would break.

Signing in on the development stack

A fresh development stack comes with one user per role, so nobody has to create accounts by hand. They are made in the armada realm when the stack starts, and a user that already exists is left alone.

Username Password Role
admin 123456 admin
staff 123456 staff
student 123456 student

Sign in at http://localhost:5174/auth, the web app's own address, from the web app or Bruno. The password is DEV_USER_PASSWORD in config/compose.dev.env; if you change it there, the next new user gets the new one.

Development only. These users exist only in the development stack, which is reachable from your own machine alone. A deployment never creates them. The admin user here is a person with the admin role in the app, not Keycloak's own administrator, whose details are KEYCLOAK_ADMIN_USERNAME and KEYCLOAK_ADMIN_PASSWORD in the same file.
