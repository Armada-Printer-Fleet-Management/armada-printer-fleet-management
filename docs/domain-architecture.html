Domain architecture

How business logic is shaped in every Python service as domain-driven design (DDD). This page shows why they exist and how the pieces fit, using print jobs as the example.

Vocabulary

Term Meaning here Example
Entity A thing with an identity, its state, and the rules that change it. PrintJob
Typed ID Each entity's own ID type, so a printer's ID cannot be passed as a job's. PrintJobId
Rule A method on the entity that allows or refuses a change. start_review(now)
Service The domain's public interface: one method per use case. PrintJobService
Repository (port) An interface for loading and saving entities, owned by the domain. PrintJobRepository
Infrastructure Code that does I/O by implementing a port: databases, network clients. SqlPrintJobRepository
DTO and mapper The proto message that crosses the wire, and the class converting it to and from the entity. PrintJobMapper

The idea: dependencies point inward

Why this is worth the structure:

  • One place for each rule. When a status transition changes, it changes on the entity, not in every handler that might move a job.
  • Rules are tested without a database or a server. An entity is plain Python, so its tests are instant and need no fixtures.
  • Storage and transport can change without touching rules. Replacing the database is a new class implementing the port.
  • One definition of a print job. The server and the desktop use the same entity, so they cannot disagree about what a job is.

How it scales

Server and desktop domains differ

They share entities, but not the way changes happen. The server is authoritative: its service loads the entity, applies the rule and saves, because only it can validate every request against current state, whichever client or concurrent caller sent it. The desktop never saves a shared entity and never applies its rule: its service passes the typed ID to a request_<action>() method on its repository port, and the server's answer, a changed entity or a RuleViolation, is the result. An entity specific to the desktop is defined in the desktop's own domain, and the desktop may save it.

In both apps the repository is a port that stays in the domain, and the domain calls the infrastructure that implements it. Infrastructure is I/O only. It holds no domain logic, and its classes are named after what they talk to, such as the desktop's ApplicationServerPrintJobs on an ApplicationServerClient base.

Testing Enforcement

Check Catches
Layer contracts (import-linter) A domain importing transport, infrastructure, generated code or a framework; domains importing each other
Structure tests A domain without its repository, service or shared entity; a service not built on the Service base; an entity that loses identity equality
Drift tests A typed ID or status missing from the proto, or a proto field the mapper forgets
IPC tests A desktop IPC call taking loose arguments instead of one request message

All of them run in CI and in the pre-push hook. To add a use case, follow print jobs: the rule on the entity, the use case on the service, and the handler or IPC call translating at the edge.
