Desktop application

How apps/desktop/ is put together: a Python backend and a React frontend, talking over a real inter-process bridge, typed end to end by a shared protobuf contract.

This page goes deeper than apps/desktop/README.md. Read the README first for the short version; come here for the diagrams and the reasoning behind each piece.

Overview

The desktop app is two separate programs. backend/ is a Python process that opens a native window (via pywebview) and renders frontend/'s built React UI inside it. They are not one process with two halves — the rendered frontend runs inside its own WebView2 (or platform-equivalent) renderer process, separate from the Python host. Calling between them is genuine inter-process communication, the same reason Electron calls its own main↔renderer channel "IPC."

Both sides depend on packages/proto/ for their message shapes, but they share no dependency graph: the backend is a uv project and the frontend a pnpm project, each with its own manifest. The only thing tying them together is generated code produced from the same .proto source.

System architecture

backend hands pywebview a single Ipc object. pywebview walks nested class instances on that object automatically (verified directly against pywebview 6.2.1), so each concrete module becomes its own namespace in JS — window.pywebview.api.application_info.version() — instead of one flat bag of methods on the root object. Adding a capability means adding one attribute to Ipc, never restructuring it.

Codegen flow

Both templates run fully offline: protoc_builtin uses the real protoc compiler installed locally (an onboarding prerequisite, like buf itself), and local: protoc-gen-es.

Running it

Mode Command What it does
Default python apps/desktop/dev_run.py pnpm build → the backend loads dist/index.html via file://. No dev server process — the same way the packaged build loads its assets (see Packaging).
Hot reload python apps/desktop/dev_run.py --dev Starts a Vite dev server on :5173; the backend window points at it directly. Editing App.tsx hot-reloads without restarting the Python process.

Packaging

python apps/desktop/build_run.py turns the two halves into one Windows program: it runs pnpm build for the frontend, then PyInstaller packages the backend and bundles that frontend build with it. The result is a folder, apps/desktop/backend/dist/<title>/, holding <title>.exe and an _internal/ folder beside it (PyInstaller's "onedir" layout). Windows only. The script prints collapsible groups when it runs inside GitHub Actions and plain step banners in a terminal.

Development versus packaged: Environment

The backend runs in two situations that look the same to the user but not to the filesystem: from source (uv run, dev_run.py), where files live in the repo tree, and from the packaged .exe, where files live in the folder PyInstaller unpacks them into. Environment.is_dev tells them apart.

The spec file

PyInstaller bundles what it can see by reading the code's imports. apps/desktop/backend/desktop_backend.spec is where anything it cannot see gets linked, and it is the file to change when a feature works from source but not from the .exe. Type checks and tests will not catch these, so run the build and launch the program after changing backend dependencies or files read at runtime.

PyInstaller lists what it could not resolve in backend/build/desktop_backend/warn-desktop_backend.txt; most entries are harmless conditional imports, so look for the package you just added. Set console=True in the spec to see start-up errors in a terminal.

Getting a build

  1. On your machine: python apps/desktop/build_run.py.
  2. Exactly as CI runs it, without pushing: on a Windows machine, act workflow_dispatch -W .github/workflows/desktop.ci.yml -j package -P windows-latest=-self-hosted runs the real package job on your own machine instead of in a Linux container. act also runs the job's needs (backend and frontend) unless you point it at a copy of the workflow without them. It cannot run the final artifact upload (it has no artifact service), so that step fails at the very end; the executable it built is under ~/.cache/act/.
  3. A build of a pull request, from GitHub, without merging: the package job never runs on pull requests, but it can be started by hand. Open the Actions tab, choose CI (desktop), press Run workflow and pick the PR's branch. The build appears on that run as the desktop-windows artifact.
  4. Automatically: every push to main or release/** builds and uploads the same artifact.

Installer

python apps/desktop/installer_run.py runs the build above, then wraps the bundle in a setup wizard with NSIS, a free, zlib-licensed installer compiler. The result is apps/desktop/installer/dist/<title>-Setup-<version>.exe. --skip-build reuses an existing bundle. --smoke-test installs the result silently for the current user, checks that the app landed, and uninstalls it again.

installer/installer.nsi names nothing itself. Every name, the version and the paths arrive as /D defines from installer_run.py, which reads them through armada_runtime.packaging.installer_info(). It copies the whole bundle, so new files in it need no installer change.

The uninstaller deletes only the exe, _internal/ and itself, so an install into a shared folder cannot take unrelated files with it. If the bundle ever gains another top-level entry, add it to the Uninstall section.

NSIS itself

python scripts/install_nsis.py installs NSIS on a developer's machine and in CI alike. It downloads the official setup program from SourceForge, refuses it unless its SHA-256 matches the value pinned in the script, and installs it silently. On a developer's machine Windows shows one administrator prompt. The setup program is not code-signed and SourceForge publishes no checksums, so the pinned hash was checked against winget's reviewed NSIS.NSIS manifest. To move to a new version, change VERSION and SHA256 together, and take the hash from a source other than your own download.

In CI the package job runs the installer build with --smoke-test, and uploads the result as the desktop-windows-installer artifact beside desktop-windows.
