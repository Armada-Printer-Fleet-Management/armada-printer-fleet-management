Slicer engine

How CuraEngine, compiled to WebAssembly, gets from its source to the web and desktop apps, and which side owns what once it is running.

What it is, and why we build it ourselves

Both clients slice models in the browser with CuraEngine, compiled to WebAssembly. We compile it ourselves, from pinned and checksummed source, in a sister repository, armada-slicer-engine. A prebuilt .wasm from anyone else would be code we could not inspect, running in our users' browsers. Here every input is pinned by hash, every release is signed by the workflow that built it, and anyone can rebuild a release and get the same bytes.

The sister repository holds only the toolchain. Everything Armada does with the engine lives in this repository, so the two never need to change together except to move to a new engine release.

From source to the apps

Developers, CI and the web image all run the same fetch script. A file whose SHA-256 does not match the pin, or which was not attested by the sister repository's release workflow for that tag, never reaches a build.

At run time: who does what

The heavy work stays where the model is drawn. Toolpaths are far too large to send over the desktop's IPC bridge or across the network, so the renderer runs the engine and passes on only what a decision needs. The decisions themselves are domain rules, shared by the server and the desktop and written in Python like every other domain.

Limit: the engine can use at most 4 GB of memory, the most WebAssembly allows, and a model that needs more stops the slice with an out-of-memory error. The ceiling is a build setting in the sister repository.
