Git hygiene guide

Development throws up situations that break this guide. It describes what to do most of the time; it is not a rigid requirement. When you depart from it, say why in the pull request.

Summary

  • Rebase only, both for syncing a branch and for merging a pull request into main.
  • Commit messages are title, bullet body, ticket line.
  • Squash your commits into one coherent commit per ticket.
  • Cherry-pick to release branches.

Developer workflow

Assumes you are working from the most up-to-date unreleased stable branch.

Rebase against main, do not merge main into your branch

Rebasing keeps commit history linear, which is significantly more organised and easier to read.

Rebasing onto the most recent main also keeps your work on top of the newest changes. When you then test, there is no chance your branch is stale. A stale branch — one with newer commits on main — risks introducing bugs, because the behaviour of the code you built against may have changed underneath you.

Merge commits add clutter. Reserve them for large feature branches whose history has become too difficult to manage otherwise.

Merge pull requests with the rebase strategy

Rebase is the default on the remote. Merge remains available, because special cases need it.

Squash your commits into one

One PR, one ticket, one commit. That is what makes the linear history readable and traceable.

The exception is when you need to cherry-pick only part of the changes later — keep those parts as separate commits.

Commit message format

Conventional commit title, a bullet list summarising the work, and the ticket as the last line. 

<type>(<scope>): <title>

- each point summarises one change

<Ticket ID> <Ticket Title>

/commit-message generates this for you. The commit-msg hook rejects anything that does not match, so this is enforced rather than encouraged.

Branch naming

KindPattern
Regular ticket developer/firstname.lastname/<ticket-id>-<ticket-title>
Large feature feature/<feature-name>
Release release/x.y.z, created automatically; see below

For a large feature, branch feature/<name> off main, and commit developer branches into that feature branch rather than directly into main.

Release branches

Release branches are live production. They are treated more carefully than main, and changes reaching them carry more risk.

Only cherry-pick minimal, low-risk changes onto them. Moving a site to the next version is a large maintenance event, not a cherry-pick.

A release branch is created by the release workflow when a version is promoted to production, and is named for that version: release/1.0.0. Only versions that reached production get one, and the last five are kept. Versions on staging are release candidates such as 1.0.0-rc.1, and never get a branch. Nobody creates a release branch by hand, except for a hot fix.

Hot fixes

Only the version in production is hot fixed. A hot fix is a new patch version on a new branch, never a commit added to an existing release branch.

  1. Fix the bug on main with an ordinary pull request. Merging it also moves the testing environment to a new build, like any other change, so the fix is tested there alongside everything else merged since the last release. Because it is on main, every future version cut from main includes it, and the bug cannot come back with the next release.
  2. Define a clone ticket for the hot fix.
  3. Cut the next patch version from production's release branch, and cherry-pick the fix: 
    git fetch
git switch -c release/1.0.1 origin/release/1.0.0
git cherry-pick -x <commit-hash>
git commit --amend          # rewrite as the clone commit message below
git push -u origin release/1.0.1
  4. The push builds release candidate 1.0.1-rc.1 and moves the staging environment to it. Test it there, then promote it to production with the release workflow, which names it 1.0.1. If it needs another change, fix main and cherry-pick again onto the same branch; the next push builds 1.0.1-rc.2. If the hot fix is abandoned, delete the branch.
  5. Whatever was on staging before the hot fix was built without the fix. Promote a new version from testing, which has the fix, and test it on staging again.

The clone ticket documents anything that went wrong during the pick, such as merge conflicts.

Clone commit message

<Original Commit Message>

Cherry-picked from <commit-hash>

<Clone Ticket ID> <Clone Title>

Keep the original subject and bullets intact, so the two commits are recognisably the same change. Fixes always land on main first and are cherry-picked from there — never the reverse.
